# SD 規格書維護與版更規範

> 本檔案是**編輯既有 SD 規格書時**要遵守的規則，跟撰寫「全新」規格書的骨架/結構規則是分開的兩件事——
> 不管這份規格是不是照那份範本建立的，**只要之後要改內容，都要照這份文件的規則**。

## 版更規則

1. **檔名維持不變**，不要把版號跟著寫進檔名去改（例如不要把 `SPEC_xxx.md` 改名成加版號的
   `SPEC_xxx_v0.2.md`）——檔名一改，所有指向這份檔案的回連結（TableSchema／Exception／
   REPORT_DEV_WORKFLOW.md 等）全部會失效。版號只記錄在文件內的「版本管控歷程」表格。
2. 「版本管控歷程」新增一列，**版次遞增**（0.1→0.2），**修訂說明寫清楚這次具體改了什麼**
   （例如「新增 rptMenuUuid 欄位」，不要只寫「調整」「修正」這種看不出內容的說明）。
3. **「修訂說明」欄位要精簡**：只寫一句話講清楚改了什麼即可，不要把版號適用範圍之類的政策說明也
   塞進這一格，那種比較長的政策/規則說明要另外寫成表格上方的一行提示（例如
   `> 版號僅反映資料庫表結構本身異動；...`），不要跟變更記錄混在同一格裡。
4. 用 `<mark>文字</mark>` 把**這次版更新增/修改的內容**標記起來（大部分瀏覽器預設會渲染成黃底
   醒目提示，不需要額外指定顏色）。
5. **只標記最新一版的異動，不要每個版本疊加不同顏色**：等到下一次版更時，先把上一版的 `<mark>`
   標記拿掉（該內容已經是「舊的、穩定的」，不再需要提示），再標記這次新改的地方。文件裡永遠只會有
   「目前這一版新改了什麼」這一種標記，不會累積成一堆不同顏色分不清楚。
6. **`<mark>` 裡面不要包住反引號（`` ` ``）格式化的文字**：反引號格式化文字有自己的灰底 code
   樣式，跟 `<mark>` 的黃底疊在一起會斷開不連續、很醜。只標記純文字說明，把欄位名稱／格式範例等
   反引號文字排除在 `<mark>` 範圍外（例如寫成 `` `make_time`<mark>（轉換為民國格式顯示）</mark> ``，
   不要寫成 `` <mark>`make_time`（轉換為民國格式顯示）</mark> ``）。
7. **「使用欄位」類清單只列欄位名稱，不要夾帶轉換/顯示邏輯說明**：不管是主文件「使用資料表」章節的
   欄位清單，還是 `TableSchema` 子文件「各報表使用欄位對照」表格，都只單純列出用到哪些欄位就好
   （例如 `make_time`），**不要**在後面加註「（轉換為民國格式顯示...）」這種行為說明——這類轉換/
   顯示邏輯的說明只在 API 說明的 OUTPUT／resultList 內容表格裡寫一次就好，維持單一資訊來源，避免
   多處說明不一致，也避免後續開發者（或子代理人）誤以為欄位清單本身就代表轉換邏輯的定義位置。
8. **`TableSchema` 子文件的版號只反映「資料庫表結構本身」的變動**（新增/刪除/改型別欄位、PK 異動
   等）。如果只是某個報表的「使用欄位對照」那欄描述文字要更新（例如某欄位顯示邏輯改變，但 DB 欄位
   本身沒變），**直接改文字就好，不用遞增 TableSchema 的版號、也不用 `<mark>` 標記**——這種變動屬於
   報表自己的需求變更，該記錄在那份報表 SPEC 自己的版本管控歷程裡，不要把兩件事混在一起，否則
   `TableSchema` 版號會遞增得很頻繁、維護成本過高。
