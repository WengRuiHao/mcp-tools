# SD 規格書撰寫範本（後端 API-SPEC，MD 版）

> 本檔案是**撰寫規則說明＋可複製骨架**，不是實際某支程式的規格。

## 撰寫原則

1. **內容只寫需求邏輯，不寫程式實作細節**：業務邏輯的敘述要讓不會寫程式的人也看得懂在做什麼
   （例如「依會計年度＋機關區間查詢」），不要寫「呼叫 XXX.checkXXX() 方法」這種程式呼叫鏈。
2. **但要標明程式位置（Controller／Service／Repository／VO／DTO）**：每個 API 一律列出實際的
   類別完整路徑＋方法名，讓人找得到對應程式碼在哪裡，這**不算**違反第1點（這是「位置指引」，不是
   「實作邏輯」）。
3. **共用的東西拆成獨立子文件，不要每份規格重複貼**：
   - 資料表結構 → 拆到 `TableSchema/{資料表名}.md`
   - 共用回應格式（自定義檢核／系統異常） → 拆到 `Exception/{文件名}.md`
   - 拆出去的子文件如果是「被特定幾份規格共用、consumer 清單列得完」（例如某張表被哪幾支報表用），
     要在該子文件裡的用途對照表「報表」欄位直接做成連結**回連**到各引用的規格文件，不要另外弄一份
     獨立清單。
   - 如果子文件是「適用範圍是全部 API」（consumer 清單會無限增長、列不完，例如共用回應格式規範），
     則不需要（也不該）列回連結。
4. **回應內容以外的通用失敗格式，只在文件最上方（規格說明區塊）說明一次**：不要在每個 API 的
   OUTPUT 都重複貼「自定義檢核時／系統異常時」那兩張表，用一句話＋連結指向共用文件即可；只有
   「成功時」的回應內容（每個 API 都不一樣）才留在各自 OUTPUT 裡。
5. **巢狀 JSON 用「每層獨立小表＋文字互相參照」表示，不要用縮排塞進同一張表**：外層表格某欄位如果
   是物件／陣列，`ElementType` 直接寫實際的 DTO/類別名稱（不要寫含糊的 `Object`），`Memo` 寫
   「內容見下方（X）」，再另外開一個編號小節（一）（二）（三）...寫該層的欄位。
6. **一律用純 markdown 表格語法，不要用內嵌 HTML `<table>`**：實際上傳到 SVN 後，正式的 SVN 網頁
   檢視工具**不會渲染內嵌 HTML**，會把 `<table>`／`<colgroup>`／`<b>` 等標籤原封不動當純文字顯示
   出來，比沒特別處理的表格更難讀（這是實測驗證過的，不是理論推測）。標籤欄位要加粗就用
   `**文字**`（標準 markdown 語法，這個沒問題），表格標題列會被大多數渲染器自動套用粗體/底色樣式，
   不用額外加粗。**欄寬不一致是純 markdown 表格語法本身的限制，沒有辦法強制等寬**，接受這個限制，
   不要為了美觀犧牲掉正式檢視環境的可讀性。
7. **INPUT／OUTPUT 的 JSON 範例一律用多行縮排格式，不要寫成單行**：不管是 INPUT 還是 OUTPUT 的
   範例，也不管巢狀多深（陣列裡的物件、物件裡的物件），每個欄位都各自一行、用 2 空格縮排，例如：
   ```json
   {
     "fiscalYear": 115,
     "budgetOrgStart": "09901"
   }
   ```
   不要寫成 `{ "fiscalYear": 115, "budgetOrgStart": "09901" }` 這種擠在一行的格式——單行在欄位一多
   或巢狀變深時會很難讀，多行縮排才能一眼看出每個欄位對應的值跟巢狀層級。

## 共用子文件骨架

### Exception 子文件（`Exception/{檔名}.md`）

- 開頭放版本管控歷程表（跟主文件一樣的 HTML table 格式）。
- 定義失敗情境有哪幾種（自定義檢核 vs 系統異常）＋各自對應的例外類別。
- 各情境的回應格式表＋JSON 範例。
- **不放**回連結清單（適用範圍是全部 API，consumer 列不完）。

### TableSchema 子文件（`TableSchema/{資料表名}.md`）

- 開頭放版本管控歷程表。
- 完整欄位清單（DB 欄位／型態／PK／說明），純資料庫層級描述，不放 Java 型別。
- 結尾放「各報表使用欄位對照」表，**報表欄位直接用連結**指回各自的規格文件（就是回連結，不要另外
  弄清單）。
- 版號什麼時候該遞增（只反映表結構本身變動，報表使用欄位描述更新不算）見 `get_sd_spec_versioning_rules` 工具回傳的內容。
