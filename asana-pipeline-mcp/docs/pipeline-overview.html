Asana Pipeline 全景圖

從「今天有哪些票該處理」到分析師 → 工程師 → 驗證師三階段自動跑完，再到換 session／換 AI 接手、票單內容被改過怎麼被抓出來——這五張圖對照目前這個 MCP 實際在跑的完整流程。

0

一次性設定

每個 Asana 專案通常只需要問使用者一次，之後永久記住，不會每次都重問。

resolve_default_project

今天看哪個專案

確認要處理的 Asana workspace / 專案，記住後同樣的觸發語句不會再問。

resolve_project_dir

對應的程式碼目錄

這個 Asana 專案要對應本機/伺服器上哪個目錄，追蹤檔案會建在裡面。

resolve_sasd_config

SA/SD 規格模式

規格放哪裡、是自己產的還是別人產的——見下方「SASD 四種模式」。

resolve_git_roots

git 版控根目錄

前後端各自的 repo 在哪，run_project_shell 執行 git 指令前會驗證這個。

2

單張票的狀態機

這是這次改版新增的重點：已經 PASS 的票，如果 Asana 內容後來被改過，會被強制打回重新分析；內容沒再變的話，則會依序落入待第一關（使用者自測＋審視 code）、待第二關（獨立測試員情境測試）兩個確認狀態，AI 判的 PASS 不等於真正結案，任何一關都不會悄悄消失在清單外。verdict 是 FAIL 時，會依 rootCause 自動路由回分析師或工程師重跑，不用停下來問使用者——兩關人類確認 confirmed:false 時也會套用同一套機制，不是另開一條人工流程。

  • 上排六個灰色方框是這張票在 status.json 裡的 stage 欄位，依序代表：
    • new — 票剛被列出來，還沒抓過內容
    • snapshot — 已呼叫 get_ticket_snapshot，票單描述＋留言已抓下來寫進 ticket.md
    • project_dir_confirmed（圖上顯示「目錄確認」）— 已知道這張票對應哪個程式碼目錄
    • analyzed — 分析師已產出 01-analysis.md
    • implemented — 工程師已修改完程式碼、產出 02-implementation.md
    • verified（綠色）— 驗證師已給出 PASS/FAIL 結論
    灰色箭頭只往右走：這六格永遠照這個順序推進，不會跳過、也不會倒退。
  • snapshot 框下面那個灰色小圈圈：每次重新呼叫 get_ticket_snapshot 抓這張票，如果內容雜湊值跟上次一樣，工具不會重寫 ticket.md、也不會把全文塞回這次回應，只回傳簡短的 unchanged: true——單純是省 token 的捷徑，跟 stage 有沒有推進無關。
  • verified 框右上角那張紅色卡片：只有這張票已經走到 verified、之後 get_ticket_snapshot 又偵測到內容雜湊真的變了，才會出現。它代表 status.json 裡另外幾個獨立欄位被改動：needs_reanalysis 變成 true、verdict 清空成 null、self_confirmation／tester_confirmation 兩關人類確認也一併清空成 null（不能讓「測過的是舊版內容」被誤認成這一版也測過）。這張卡片刻意畫成只掛在 verified 框旁邊、沒有箭頭連回任何更早的框——因為 stage 欄位本身完全沒有變動，這張票的 stage 永遠還是顯示 verified；真正改變的是「這張票該不該被當作已經處理完」，不是它處理到哪一步。
  • 紅框下方那張較寬的「verdict: FAIL → rootCause 根因分流」卡片：驗證師判 FAIL 時，呼叫 advance_ticket_stage 必須帶 rootCause（"analysis" 或 "implementation"），AI 依這個判斷自動跳回分析師或工程師重跑，不用停下來問使用者；consecutive_fail_count 由工具機械式維護（FAIL 累加、PASS 歸零），達到門檻（needs_human_review，預設連續 3 次）就不再自動重跑，要停下來問使用者。這個入口不只給 AI 自己判 FAIL 用——下面兩關人類確認任一關 confirmed: false，也會導向同一套機制。
  • 綠框下面依序是兩張黃色「待確認」卡片：verified 且 PASS、內容也沒再變的情況下，票單會先落入第一關——使用者自己實測＋審視程式碼品質；呼叫 record_self_confirmation({ confirmed: true }) 之後才會進到第二關——另一位獨立測試員的情境測試。兩關都要 confirmed: true，票單才會進入最下面的綠色「已結案」；任一關 confirmed: false 會把 verdict 重設回 null、標記 humanRejected: true，重新落入上面那套 FAIL 根因分流機制，不是留著等人工事後自己判斷、也不是另開一條獨立流程。第二關的工具本身也會擋下「第一關還沒過就想記錄第二關」的呼叫。
灰＝一般階段方框 綠＝verified 且已有結論 紅＝需要重新分析的警示
3

SA/SD 規格四種模式

resolve_sasd_config 找不到設定時才需要逐題問，四選一之後同一個 Asana 專案不會再問（unregistered 除外，那個每張票都要單獨問）。

external

規格是客戶/第三方產的

只能參考，絕對不能建議修改 SD 本身，只能調整程式碼去配合它。

self

規格是自己團隊產的

可以在報告裡建議修改段落，但不會寫回 SVN（唯讀），交人工事後更新。

self-generated

沒有既有規格，AI 自己維護

真的寫進 sdOutputPath 指定的本機檔案，寫完提醒使用者可以自行傳到 SVN。

unregistered

不登記，逐票詢問

唯一每張票都要單獨問「有沒有 SD」的模式，不會被專案層級的設定省略掉。

01/02/03 互相同步

跟上面「票單狀態機」不同軸向：那組管「票單原文 vs 追蹤系統」，這組管「追蹤系統內部 01/02/03 三份文件彼此」——這條 pipeline 曾經實際發生過工程師階段反覆修正十幾輪、02-implementation.md 一路追加，但 01-analysis.md 完全沒同步，全靠使用者事後肉眼發現。

步驟 1 的 list_pending_tickets 也會用 Asana 的 modified_at 做便宜初篩：已經 PASS 的票如果 modified_at 跟上次不一樣，會標記 contentChanged: true 重新排進待處理清單，交給步驟 2 的雜湊比對做最終確認。全部票單處理完後，整理成表格（票單／專案目錄／SD 模式／結果／備註）交給使用者，程式碼異動可能已經 commit，但一律不會自動 push。
