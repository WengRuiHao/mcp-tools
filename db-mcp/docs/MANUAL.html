🗄️ db-mcp 使用手冊

資料庫裡的答案，用問的就好

這是給 AI 助理用的一個小工具，讓它能幫你查資料庫裡的表格結構、抓資料、比對環境差異。這份手冊用白話文說明它怎麼運作、能查什麼、什麼時候該用哪一種問法。

這是什麼 運作方式 資料模型 工具總覽 唯讀把關 實際範例 常見問題

01 這是什麼？

公司的系統背後都有資料庫存著實際的資料——客戶、訂單、設定值，任何東西。過去要查一張表長什麼樣子、資料庫裡到底存了什麼，得自己開資料庫工具、寫 SQL 一步步查。 現在你可以直接用中文跟 AI 助理說「幫我看某張表的結構」「這張表裡有哪些資料」，AI 助理會透過 db-mcp 這個工具去資料庫把資料抓回來，整理成看得懂的白話文回答你。

這個工具**只能查詢、不能亂改資料**——真的會執行 SQL 的工具內建了寫死在程式碼裡的把關規則（見下方「唯讀把關」），不是靠 AI 自己記得小心，想繞都繞不過去。

03 資料模型

每個資料庫連線都掛在某個「建置案」底下。同一個建置案的 dev/test/staging/正式機各自是一條獨立連線，但共用同一份結構快取——不用每個環境都重新摸一次資料庫，查詢速度也快很多。

📁 某個建置案
dev test staging prod ⚠️
↓ 各自同步進 ↓
同一份 schema 快取（表 / 欄位 / 主鍵外鍵 / 索引 / 你寫的筆記）

連到標記為 prod（正式機）的連線時，查詢結果會多附一句警示，提醒這是正式環境；其他環境沒有這個額外提醒。

04 工具總覽

總共五大類、15 個工具。每一類點開來看，裡面有實際的工具名稱（給負責設定的 IT 人員對照用）跟白話說明。

📁

專案

建置案/翻修案的分組管理

 ▶
可以這樣問：「目前登記了哪些專案？」
寫入db_project_create建立新的專案分組
唯讀db_project_list列出所有已登記的專案
唯讀db_project_get看單一專案的詳細資料 + 底下所有連線（不含密碼）
🔌

連線

每個環境的資料庫帳密怎麼登記

 ▶
可以這樣問：「這個專案底下有哪些資料庫連線？」
寫入db_add_connection在某個專案底下新增一筆連線設定
唯讀db_list_connections列出連線（不含密碼）
唯讀db_test_connection實際連一次資料庫，確認連線設定真的可用
🧩

Schema 結構

表、欄位、主鍵外鍵長什麼樣子

 ▶
可以這樣問：「這張表有哪些欄位？」
唯讀db_schema取得某個連線的完整結構（表/欄位/PK/FK/索引/VIEW/FUNCTION/PROCEDURE）
唯讀db_search_tables關鍵字搜尋表名/欄位名，不用整包結構一次全塞進對話
唯讀db_diff_schema比對同一專案底下兩個環境的結構差異
唯讀db_export_ddl把結構匯出成 DDL 文字，留存文件用
📝

表格筆記

AI 分析出來的表格用途，記下來以後不用重查

 ▶
可以這樣問：「這張表之前有沒有留下什麼筆記？」
寫入db_annotate_table把表格用途寫成筆記，跨 dev/test/prod 環境共用
唯讀db_list_notes列出某個專案目前所有的表格筆記
🛡️

查詢執行（唯讀把關）

真的會執行 SQL 的工具，內建硬性安全規則

 ▶

這一組工具會真的對資料庫送出 SQL，所以內建了寫死在程式碼裡的把關——不是靠 AI 自己記得小心，偵測到寫入/刪除類語句一律拒絕執行。

SELECT * FROM users WHERE id = 1 ✅ 放行執行
UPDATE users SET name = 'x' ❌ 拒絕，退回請你手動執行
WITH cte AS (DELETE ... RETURNING *) SELECT * FROM cte ❌ 拒絕（藏在子查詢裡也擋得住）

只要偵測到 INSERT/UPDATE/DELETE/DROP/ALTER/CREATE 等寫入或結構異動關鍵字，就算包在 CTE 或子查詢裡也一樣擋下來——寧可誤擋，不會誤放。真的要寫入時，工具會請你把 SQL 轉交給負責設定的人手動執行。

可以這樣問：「幫我查一下這張表裡的前 20 筆資料」
把關db_query執行唯讀 SQL，只放行 SELECT/WITH/SHOW/DESCRIBE/EXPLAIN
唯讀db_sample_rows免寫 SQL，直接看某張表前 N 筆資料長什麼樣子
把關db_explain對 SQL 跑 EXPLAIN 分析執行計畫，同一套把關規則

幾個常見情境，示範怎麼問、AI 助理在背後做了什麼。

情境一：了解一張表的結構

會員資料表裡有哪些欄位？
這張表有 12 個欄位，主鍵是 member_id，跟訂單表之間有一個外鍵關聯……（附上完整欄位清單） 背後呼叫：db_schema

情境二：不小心問了會改資料的問題

幫我把這個帳號的狀態改成停用。
這需要執行 UPDATE，我不能直接跑寫入語句。我幫你把 SQL 準備好了，麻煩你自己在資料庫工具裡手動執行：UPDATE accounts SET status = 'disabled' WHERE id = ... 背後呼叫：db_query（被唯讀把關拒絕，回傳待手動執行的 SQL）

06 常見問題

AI 助理會不會不小心改到或刪除資料庫裡的資料？

不會。真的會執行 SQL 的工具內建寫死在程式碼裡的把關，偵測到任何寫入/刪除/結構異動語句一律拒絕執行，就算藏在子查詢裡也擋得住。真的需要寫入時，工具只會準備好 SQL 交給你自己手動執行。

查詢結果為什麼有時候會多一句警示？

連到標記為 prod（正式機）的連線時，回應會多附一句「這是標記為 prod 的連線，請小心操作」的提醒，其他環境（dev/test/staging）沒有這個額外提醒。

第一次用某個資料庫連線要先做什麼？

建議先確認連得上，再建立結構快取——之後查表格、搜關鍵字、看資料範例都會快很多，也不用每次都重新連線摸一次資料庫。

如果我需要真的修改資料庫裡的東西怎麼辦？

請 AI 助理把需要的 SQL 準備好，交給負責設定的人在資料庫工具裡自己手動執行——這支工具設計上刻意不讓 AI 自己動手寫入，是有意的安全邊界，不是還沒做完的功能。
