Asana Pipeline 全景圖

從「今天有哪些票該處理」到分析師 → 工程師 → 驗證師三階段自動跑完，再到換 session／換 AI 接手、票單內容被改過怎麼被抓出來、追蹤檔案被繞過 MCP 直接改過又怎麼被抓出來、跑完之後需要人工處理的事項怎麼持久化——這七張圖對照目前這個 MCP 實際在跑的完整流程。

0

一次性設定

每個 Asana 專案通常只需要問使用者一次，之後永久記住，不會每次都重問。

resolve_default_project

今天看哪個專案

確認要處理的 Asana workspace / 專案，記住後同樣的觸發語句不會再問。

resolve_project_dir

對應的程式碼目錄

這個 Asana 專案要對應本機/伺服器上哪個目錄，追蹤檔案會建在裡面。

resolve_sasd_config

SA/SD 規格模式

規格放哪裡、是自己產的還是別人產的——見下方「SASD 四種模式」。

resolve_git_roots

git 版控根目錄

前後端各自的 repo 在哪，run_project_shell 執行 git 指令前會驗證這個。

2

單張票的狀態機

用白話講一遍：一張票依序經過六個步驟。驗證沒通過，AI 會自動回頭修正，不用你操心；驗證通過了也還不算真的結束，要等你自己測過、看過程式碼才算數；如果 Asana 上的票單內容後來又被改過，AI 會自動重新分析，不會用舊資料繼續做。

  • 六個灰色方框是這張票目前走到哪一步：new（剛收到）→ snapshot（抓過內容）→ project_dir_confirmed（知道程式碼在哪）→ analyzed（分析完了）→ implemented（程式碼寫完了）→ verified（驗證完了，綠色）。只會照順序往前走，不會跳過也不會倒退。
  • 上方兩張虛線小卡片是「特殊情況」提醒：左邊藍色的是只有 AI 自己維護規格文件的專案才會出現的額外一步——AI 把規格寫成草稿讓你確認，你打回意見的話 AI 會改完再讓你確認一次；依專案設定的 specOrder，這一步可能卡在「分析問題」跟「寫程式碼」之間（先規格後程式碼，確認過才動手寫），也可能卡在「寫程式碼」跟「驗證結果」之間（先程式碼後反推規格，工程師先寫完，AI 才依實作反推補一份規格）。右邊紅色的是如果 Asana 上的票單內容後來又被人改過，AI 會自動當作要重新分析，不會用舊資料繼續做。
  • 驗證結果分成兩條路：沒通過（紅色）——AI 自動回頭修正、重新驗證，不用你介入，只有連續失敗太多次才會停下來問你；你自己測試後回報有問題，也是走這條路。通過了（黃色）——先進入「待你確認」狀態，AI 覺得沒問題不代表真的沒問題，要等你自己實測、看過程式碼，確認沒問題（綠色「真的完成了」）才算真正結束。
灰＝一般步驟 綠＝已驗證／真的完成 黃＝等你確認 紅＝沒通過／需要重新分析 藍＝規格先定案（僅特定專案）
3

SA/SD 規格四種模式

resolve_sasd_config 找不到設定時才需要逐題問，四選一之後同一個 Asana 專案不會再問（unregistered 除外，那個每張票都要單獨問）。

external

規格是客戶/第三方產的

只能參考，絕對不能建議修改 SD 本身，只能調整程式碼去配合它。

self

規格是自己團隊產的

可以在報告裡建議修改段落，但不會寫回 SVN（唯讀），交人工事後更新。

self-generated

沒有既有規格，AI 自己維護

唯一會多走 sd_drafted 規格確認關卡的模式：「規格撰寫者」角色產出草稿寫進 sdOutputPath，使用者 record_spec_confirmation 確認過才能繼續（見上方區塊 2 補充圖）。額外要登記 specOrder：spec_first——規格先定案，工程師才動手寫程式碼；code_first——工程師先依分析結果直接寫程式碼，規格撰寫者再依實際改動反推補一份草稿，一樣要確認過票單才能推進到驗證完成。

unregistered

不登記，逐票詢問

唯一每張票都要單獨問「有沒有 SD」的模式，不會被專案層級的設定省略掉。

換 session／換 AI 接手

追蹤狀態落地在磁碟上，不是活在對話記憶裡——接手時該讀「摘要」還是「全文」，成本差很多。

粗實線＝預設路徑，成本低 虛線＝按需路徑，成本較高
5

01/02/03 互相同步

跟上面「票單狀態機」不同軸向：那組管「票單原文 vs 追蹤系統」，這組管「追蹤系統內部 01/02/03 三份文件彼此」——這條 pipeline 曾經實際發生過工程師階段反覆修正十幾輪、02-implementation.md 一路追加，但 01-analysis.md 完全沒同步，全靠使用者事後肉眼發現。

6

外部修改偵測

跟上面「01/02/03 互相同步」是不同軸向的比對：那張比的是「兩份都是這個 MCP 自己以前記錄的雜湊」彼此對不對得起來；這張比的是「這個 MCP 記錄的舊雜湊」跟「磁碟上現在真正的內容」對不對得起來——只有這組比對抓得到使用者或沒走這條 pipeline 的 AI 直接手動編輯追蹤檔案的情況。

7

待人工處理清單持久化

過去「這張票需要你確認」「這個 SQL 只能你手動執行」這類提醒只在聊天回覆裡講一次，換個 session、關掉對話視窗就找不到了。現在整份寫進磁碟上的一份 Markdown 檔案，不靠聊天記錄留存。

步驟 1 的 list_pending_tickets 也會用 Asana 的 modified_at 做便宜初篩：已經 PASS 的票如果 modified_at 跟上次不一樣，會標記 contentChanged: true 重新排進待處理清單，交給步驟 2 的雜湊比對做最終確認。全部票單處理完後，整理成表格（票單／專案目錄／SD 模式／結果／備註）交給使用者，程式碼異動可能已經 commit，但一律不會自動 push。
