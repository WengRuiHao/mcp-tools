# SA／SD 撰寫標準範本

使用者在實際走完一次規格先行流程後確認：「目前這樣就是完整版，SA、SD 就要依照這個等級去撰寫」。這個資料夾是確認過的標準範本，之後所有 SA、SD、資料表結構文件都以此為準。

## 範本檔案
| 檔案 | 用途 |
|---|---|
| SA-範本.md、SA-範本.docx | SA（客戶版）的樣子；docx 是由 md 轉出的 Word 版 |
| SD-範本.md | SD（自足版）的樣子 |
| 資料表結構文件-範本.md | 資料表結構文件（每張表一份）的樣子 |
| mockup-狀態切換範例.html | 可切換狀態的 mockup 範例，用來截各種狀態的畫面 |
| sa-images/ | 範本引用的畫面截圖（整體畫面與各種狀態，路徑相對於文件） |
| tools/md2docx.py | md 轉 Word 的原型（python-docx，支援圖片、表格、標題） |

## SA 標準（給客戶看）
1. 不可有工程或程式用語，不可有空洞章節（例如「已確認的決定」「依據附錄」「純後端」「共用畫面元件」），不可寫「說明這段文字為什麼存在」的句子。
2. 有基本資料表與版本管控歷程；確認的細節濃縮在修訂說明，不放正文。
3. 結構：功能目的 → 畫面 → 操作說明 → 規則 → 匯出內容 → 提示。
4. 規則、欄位、格式類內容一律用表格；只有有先後順序的操作步驟用編號清單。
5. 前端檢核（送出前擋下，提示在欄位下方）與後端回應（送出後，提示在訊息區）分開寫；警告訊息用實際畫面截圖呈現，每個前端功能附各種狀態的畫面。
6. 交付格式為 Word（由 md 轉出，圖片嵌入）。

## SD 標準
1. 依 MCP 既有 SD 範本：程式基本資料表、版本管控歷程、目錄、規格說明、API 說明。
2. 章節順序：使用資料表 → 前端功能與 API 對應表 → 共用方法清單（共用方法、位置、類型、被誰使用、說明）→ 共用回應與錯誤碼（含「檢核位置」與「前端提示位置」）→ API 說明。
3. 每個 API 標明控制層、服務層、查詢層的檔案與方法，以及使用的共用方法；不需要獨立的分層對照表。
4. 不可指向內部過程檔案，不可有「選用」這類不確定寫法，不可有說明本文件用途的句子。
5. 資料表欄位不放在 SD，使用資料表只放連結；結構另外寫成資料表結構文件。
6. 交付格式為 md。

## 資料表結構文件標準
每張表一份：版本管控歷程、欄位清單、索引、各規格使用欄位對照（連回規格）。

## 通用原則
- 正式交付物（SA、SD、資料表結構、流程圖）必須自足：不指向內部過程檔案，圖片路徑為相對於文件的固定位置。
- 內部過程檔案（SQL 設計說明、規格驗證報告、審查報告、實作說明等）不交付。
