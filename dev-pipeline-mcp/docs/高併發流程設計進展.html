一、問題背景

現有流程為單一功能設計（例：會員匯出訂單 Excel）。開發高併發系統時，下列問題會影響分析師判斷，現有流程與說明書沒有涵蓋：

  • DB 設計：寫入熱點、鎖、冪等鍵、分區、資料量成長
  • MQ 設計：傳遞語意、重複投遞、排序、重試與死信、積壓上限
  • 失敗情境：逾時、重複請求、並行衝突、下游不可用、空值（空指標）、記憶體（OOM）
  • 非功能需求：尖峰人數、處理量、回應時間、可用時間、資料量與保存期

三、兩種情境與流程順序（兩者都要有）

新系統／翻新（系統層，做一次）既有系統單一功能，以及新系統裡的每個功能（功能層）
架構是否存在還沒有，要決定已存在，要遵守
架構師角色決策者：DB 引擎、MQ、快取、一致性模型、分區符合性檢查者：現有架構撐得住嗎？要不要加 MQ 或快取？多數寫「沿用現有，無需新增」
順序基線調查 → 技術選型（語言與框架）→ 架構師（先於 SA）→ 產出「架構決策書」存專案層級基線調查 → 技術選型（語言與框架）→ SA → 架構符合性與 MQ 設計 → DB → SD
非功能需求數字來源使用者在系統層直接回答整個系統的目標數字（尖峰人數、資料量、可用時間等）SA 繼承系統層數字，只補功能特有部分；既有系統沒有系統層數字時由 SA 在功能層寫
為什麼順序這樣架構限制 SA 能承諾什麼（最終一致就不能寫「按下去立刻看到」）要先知道功能與預估流量，才能判斷現有架構夠不夠
功能層：技術選型 → SA（含非功能需求）→ 架構 → DB → SD → 實作與驗證 系統層：技術選型 → 架構師（決策版）→ 架構決策書 →（之後每個功能走功能層）

新系統是幾十個功能，架構只做一次；新系統的第一個工作項目就是「架構」，之後的功能與既有系統單一功能是同一條流程，不用兩套。

實作方式（已查證）：同一角色不能依情境換上游，所以採兩個互斥角色 arch-pre（baseline==greenfield，SA 前）與 arch-post（baseline==brownfield，SA 後），共用同一份說明書與產出物。新增 highRisk 條件需改 buildWhenContext、KNOWN_WHEN_KEYS、status 欄位與約 7 處呼叫端。

技術選型拆成兩層 已決定

  • 前層「技術選型」：只選語言與框架，對所有需求生效，維持在 SA 之前，mockup 與 SA 仍能取得前端技術資訊。
  • 後層（DB 引擎、是否用 MQ、是否用 Redis 或快取等深入取捨）：移到 SA 之後，併入架構角色，使用 SA 的真實數字決定，不再需要「依賴的假設」與退回核對。取捨表（被否決方案、理由、重新評估條件）一併移到架構角色。
  • 既有系統：資料庫種類直接沿用基線調查寫的內容，不另外選。只有新系統或高風險才進入架構角色做 DB 取捨。
  • 架構角色加「語言選擇衝突檢查」：檢查語言與框架的執行緒模型、記憶體特性有無與非功能需求衝突（例：OOM 風險），衝突時退回技術選型。
讀碼查證：技術選型的檢查 tech-stack-check.ts 固定要求 9 列：前端語言、前端框架、前端元件庫、後端語言、後端框架、資料庫種類、資料庫版本、建置與測試工具、主要版本。因此這個拆分必須動檢查，不只是加動態說明；連帶影響基線調查說明書（「現有技術棧」含資料庫）與 DB 設計師對資料庫種類的依賴。

五、非功能需求項目（預設 9 項，開放專案設定）

驗證師抽查對照 SD 的日誌事件表，在程式碼中搜尋事件名是否存在（事件名是固定字串，用搜尋即可）。已決定
SA需求中標出「哪些業務事件事後必須能查到」。已決定
SD新增日誌章節：每個 API、每個失敗情境都對應一個日誌事件與欄位。高風險的失敗模式表多一欄「留下什麼痕跡」，不可空白。已決定
審查員檢查表加一問：「出事時只看日誌能否還原發生什麼」。已決定
可程式檢查日誌章節存在；失敗情境表每列的日誌事件欄非空；日誌事件名不重複；欄位名稱屬於規定欄位。已決定
限制流程只能檢查 SD 有寫日誌設計；程式碼層只能靠搜尋抽查事件名是否出現，查不到是否在對的位置、是否真的會被執行。限制

6.2 安全設計：稽核軌跡

項目內容狀態
方向被設計的系統內要有稽核軌跡（誰在何時對什麼資料做了什麼），與日誌分開；不是流程引擎本身的操作軌跡。已決定
適用範圍所有功能的寫入類 API 都要二選一（對應稽核事件，或寫「不需稽核」加理由）；敏感資料讀取、權限變更、匯出，只在 SA 標了敏感資料或 highRisk 時才要求。已決定
驗證師抽查對照 SD 的稽核事件表，在程式碼中搜尋事件名是否存在。已決定
與日誌的差別日誌給工程師除錯，可輪替、可遺失；稽核軌跡給安全與究責，只能新增、不可改刪、有保存期限、可依業務主鍵查詢。兩者共用追蹤編號以便串起來。說明
固定欄位操作者身分與來源、時間、動作、對象（資料類型與主鍵）、結果、追蹤編號；變更前後的值中，敏感欄位只記遮罩或雜湊。已決定
需稽核的操作登入登出與授權失敗；權限變更；敏感資料讀取與匯出；金流與狀態變更；管理操作與設定變更。已決定

6.3 安全設計：認證授權

項目內容狀態
方向凡是關於授權的部分都不寫死，另外設計成可動態調整：被設計的系統要有統一的授權模組與其管理功能。角色、權限指派、角色與權限的對應、資料範圍規則（如業務只能看自己的客戶）、預設值，全是資料，可在執行中調整，不需改程式或重新部署。各功能只宣告「需要哪個權限」並呼叫該模組判斷。已決定
適用範圍適用任何系統，不限高風險。指系統內的授權模組，不是流程引擎新增角色。已決定
一般系統由誰寫授權決策選 A：授權決策放專案層級文件，由第一個需要授權的功能的 SA 一併產出（沿用現有機制，或新建授權模組）；功能層檢查所有系統一律適用；不改架構角色的啟用條件。已決定
唯一不能動態的權限碼本身：它是程式碼用來標示「這個動作受保護」的識別字，必須寫在程式與登記表裡，但誰擁有它是資料。已決定
授權模組不可用時預設拒絕，此預設固定，不做成可在執行中切換的開關。已決定
降級放行名單模組不可用時仍可放行的權限碼，只能是標為公開的權限碼；名單寫在部署設定檔（可寫死，不做本地快照），維護權限只給 admin；每次異動寫稽核並附理由。（取代原先「例外名單做成資料維護」的想法，僅限降級名單。）已決定
授權模組的管理功能角色維護、權限指派、資料範圍規則維護、變更即時生效（含快取失效）、所有變更寫稽核；本身是要開發的功能，要有自己的 SA 與 SD。已決定
系統層（架構決策）授權模型（角色型、屬性型或混合，由架構師或 SA 決定，流程只強制「必須寫明」）、在哪裡統一攔截、權限資料存放（資料表）、快取與失效方式；決策寫進專案層級文件。已決定
功能層SA 列出「資源 × 動作」。SD 每個 API 標「權限碼」，或標「公開」加理由；不得在 SD 寫死角色名稱、角色與權限的對應、或「只有某部門／某身分才能…」之類的資料範圍條件；資料範圍引用授權模組的規則名稱。已決定
失敗模式（高風險）快取過期或失效失敗時的處理；權限變更後生效的最長延遲要寫成數字。已決定
權限碼登記表放專案層級文件（共用批次 1P 基礎建設）；新功能需要新權限碼時先登記，SD 的權限碼必須存在於登記表。已決定
既有系統已有授權機制就沿用，由基線調查記錄，不重做。已決定
可程式檢查每個 API 有權限碼或「公開」理由；權限碼格式正確且在登記表中；SD 內出現角色名稱字樣時警告（先做警告等級）。已決定
限制授權模組要先於其他功能完成，但引擎沒有「功能之間的先後依賴」機制，只能靠人安排順序。限制

5 專案層文件並行寫入衝突兩個功能同時改模組地圖或權限碼登記表，後存的會蓋掉先存的。決定：以「段落」為單位寫入（例如只改某一個模組條目），每段有固定鍵值；寫入帶讀取時該段的版本（內容雜湊），版本不符拒絕並要求重讀後只重做自己的改動；跨段限制（如循環依賴）在合併後重新檢查；每次寫入記錄功能編號、時間、改動摘要於專案層變更紀錄。理由：可能多人分工。實作複雜度高，放批次 1P，現有雜湊機制能重用多少尚待唯讀查證已決定
6 地圖與程式碼不一致審查員只查 SD 的資料表有沒有越界，沒查實際程式碼。決定：地圖每個模組多一欄「對應的程式目錄」（可多個，例如前後端分開）；驗證師掃描引用，模組 A 引用 B 不屬於其對外介面清單的程式、或引用了 A 未宣告依賴的模組，標為違規；第一版只警告不擋住，累積準確度後再決定是否升級；只掃本次改動的檔案；未歸類區與歷史例外不檢查；第一版只支援專案設定檔宣告的語言，掃描規則可設定。尚未查證引擎能否讀程式碼做這類檢查（目前檢查多只看文件）已決定
7 跨模組需求變更模組 A 需要 B 的資料多一個欄位，但資料只有 B 能改，目前沒有提出變更請求的路徑。決定：A 的 SD 標註「需要 B 提供」即為變更請求；請求登記在專案層（提出方功能、被請求模組、需要的內容、狀態：待處理／處理中／已完成／已拒絕）；請求視為 B 的新功能或併入 B 進行中的功能，B 的 SA 回應接受、修改後接受、或拒絕並寫理由；請求未完成前，A 依賴的能力視為未完成，套用 7.1 擋住規則（可臨時放行須寫理由並記稽核）；被拒絕時 A 自動退回 SD 重新設計並走 7.3；B 完成後新介面登記到其對外介面清單，請求才標已完成；請求方 SD 審查員確認內容寫清楚，接受或拒絕由 B 的 SA 決定，不另開本人確認；多個功能提出同一請求時第一版不自動合併，由 B 的 SA 手動標註合併已決定
8 模組或功能下線移除時要更新地圖、處理孤立資料與依賴方。決定：下線走「下線」類型的工作項目，SA 寫明範圍與理由；影響清查由地圖機械產生（依賴它的模組與功能、擁有的資料表、登記的介面／權限碼／跨模組情境）；仍有依賴方就擋住；資料處理二選一：移交給另一個模組擁有，或封存後刪除（不接受留著不管）；刪除資料屬不可逆，套用 7.4 須本人確認並寫備份方式；完成後地圖條目標「已下線」保留不刪除，介面與權限碼標廢止；棄用期不強制，只有對外介面被其他模組使用時才要求；下線整個模組須先逐一下線其所有功能；只在 multiModule 開啟時要求。引擎目前沒有「下線」類型的工作項目，需新做，與層級機制最小實作屬同類基礎工作已決定
9 效能預算分配系統整體回應時間目標要拆到呼叫鏈上每個模組。決定：架構決策書（容量規劃節）針對關鍵情境列整體目標（回應時間、吞吐量、可用性），情境沿用缺口 4 的跨模組情境清單；每個情境把目標拆到鏈上每個模組並留餘量（至少 10%，沒留餘量審查員退回）；功能層的回應時間目標不得超過所屬模組在該情境的預算，審查員檢查；超出預算走 7.3 變更回溯（重新分配或改設計）；預算由架構角色提出、本人確認（併入架構決策書確認）；第一版不自動計算，只要求總和不超過整體目標；只在 highRisk 與 multiModule 同時開啟時要求。限制：預算只是設計承諾，壓測暫緩所以無法驗證實際達標已決定

八、系統 BPMN

項目決定
範圍與位置系統層，做一次。順序：技術選型 → 系統 BPMN（業務流程） → 架構師 → 架構決策書。架構師在 BPMN 上標出非同步邊界與訊息主題；功能層 SA 對照 BPMN 說明自己是哪一段流程。
格式真正的 BPMN 2.0（.bpmn XML），不用 mermaid 近似（使用者決定）。
性質先做內部檔（架構師與 SA 使用）。之後要給客戶時，另做「整個系統簡化版 BPMN」（使用者決定，列為後續）。
與 flow.mmd 的分工flow.mmd 是單一功能內的處理步驟（SD 內）；系統 BPMN 是端到端、跨角色與跨系統（泳道、事件、閘道、訊息事件）。
可程式檢查每流程有起點與終點；閘道分支都有條件且無死路；每個任務屬於某泳道；每個訊息事件有生產者與消費者；BPMN 任務與 SA 功能互相對應（先做警告等級）。
.bpmn 檔不好開：使用者已同意「HTML 檢視檔」做法。
  • 引擎隨每個 .bpmn 自動產出一份獨立的 .html 檢視檔：內嵌 bpmn-js，雙擊即可用瀏覽器開啟，不需安裝軟體，也不必連網。
  • 備用：Camunda Modeler（免費桌面程式）、draw.io、bpmn.io 網站（在瀏覽器本機執行）可開啟 .bpmn。

十三、已知限制

  • 流程只能強迫「有寫」與「有證據」，不能保證設計正確。
  • 審查員與作者同類模型，可能共享盲點，所以新決策類的架構確認需要使用者把關。
  • 高風險項目被擋回與打回的機率會變高。
  • 本次不做：壓力與併發測試層、程式碼層級空指標與 OOM 靜態檢查、後端交稿前自檢。
  • 日誌與稽核事件只能用搜尋事件名抽查，查不到是否在對的位置或真的會被執行。
  • 授權模組須先於其他功能完成，但引擎沒有功能間的先後依賴機制。
  • 效能預算只是設計承諾，壓測暫緩所以無法驗證實際達標。
  • 程式引用掃描能否實作尚未查證，第一版只警告；只掃改動的檔案，沒改動但已偏離的模組不會被發現（7.7 第 8 項暫不做全面檢查）。
  • 段落式寫入與版本比對複雜度高，現有雜湊機制能重用多少待查證；批次 1M 依賴多個新引擎機制，是整個設計的風險點。
  • 動態說明書字數上限 1200 字與三輪新增檢查的總量衝突，需在實作前估算，超出者條件附上（7.9 第 1 項）。
  • 不支援跨專案系統：模組地圖與專案層文件綁單一專案目錄，系統拆成多個 repo 時跨專案介面不進清單（7.8 第 1 項）。
  • 契約範例只驗證範例涵蓋的情形，不能取代真實整合與壓測。
  • 實作前仍待確認：SD 結構檢查是否容許 API 章節後多出章節（sd-api-parse.ts 的章節結尾判斷）。
